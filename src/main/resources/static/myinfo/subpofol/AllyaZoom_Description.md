## 예상되는 문제와 예상해결방법
# 대부분의 작업들을 비동기적으로 동시성을 고려하여 설계했지만 동시성을 구현하지않은 것들이 있음
- 라우터를 통해 외부 API를 호출하는 작업(브리핑 출력 미리보기)
- 목적이 출력 형식을 보는 것이니 브리핑별 템플릿을 만들어 외부 API 호출하지 않도록 하는것이 가장 단순한 해결방법
- 비동기 병렬처리로 할수도 있지만 외부 API 요청 리밋에 걸릴수있음
- 작업큐에 넣어서 순차 처리하는 방법이 중복되는 요청은 한번만 요청하고 
  배치요청이 가능한경우 묶어서 요청하여 요청수 자체를 줄이고 요청 리밋을 조절도 가능할것이라 판단됨

# 대규모 트래픽?
- 대규모 트래픽을 경험해본적은 없지만 예상으로 적어본다.
- 현재는 스케줄러가 DB에 등록된 브리핑을 조회해서 조건에 맞는 브리핑을 작업큐에 *하나씩* 추가하는중
- 먼저 규모에 맞게 테이블을 생성한다. (ex. Shard.id,Shard.count)
- 예를들어 4개의 레코드를 생성하고 id는 PK, count는 디폴트=0 으로 만든다.
- 브리핑 등록시 Shard 테이블의 count값중 가장 낮은 값을 1올리고 해당 id값을 같이 저장 (삭제시는 내린다.)
- 스케줄러를 Shard 테이블의 레코드 만큼 병렬처리하고 스케줄러별로 Shard.id를 부여한다.
- 각각의 스케줄러는 db에서 해당 id를 가진 브리핑만 골라서 조회한다.
- 조건에 맞는 브리핑을 적당한 청크로 *묶어서* 작업큐에 저장한다.
- 작업큐 테이블은 중복방지용 유니크키 세팅이 되어있다. (ex. 핸들러 + 파라미터)
- 필요하다면 워커도 위와 같은 방법으로 처리한다.
- 워커는 캐시를 우선조회한다. (구현되어있다.)
